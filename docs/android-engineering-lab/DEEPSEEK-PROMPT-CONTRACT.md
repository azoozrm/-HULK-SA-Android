# HULK SA Android — DeepSeek Task Prompt Contract

This is the adopted task-packet method for ChatGPT / Sol coordination and the normal
OpenCode / DeepSeek executor. Read it explicitly before drafting or executing a substantive
Implementation/Correction packet. Referencing a filename does not load its contents.

Current owner instructions define scope and may narrow the standing implementation workflow
in root `AGENTS.md`. This method grants no additional authority. Read the live
`TASK-EXECUTION-CONTRACT.md`, applicable override, lab, physical and subsystem contracts;
do not replace them with copied chat text, research, or template examples.

## 1. One bounded result

- Write the executor handoff in English in one copyable code block. Preserve Arabic labels exactly.
- State NEW or RESUME. NEW starts a genuinely new atomic task at the verified official HEAD.
  RESUME preserves the existing task/worktree/branch/PR, accepted changes and valid evidence.
- Lead with the owner's observed problem and exact requested result. Separate the symptom from
  the source-confirmed cause; do not infer dp values from a photograph.
- Identify the exact screen/element, property or inseparable behavior, and a verified target
  value/adaptive expression or exact accepted source reference for the executor to resolve.
- Preserve accepted neighbors, dimensions, text, assets, callbacks, state and focus ownership.
  Do not add unrequested resizing, truncation, font/color changes or a general redesign.
- Include relevant normal/focused/selected states. For ambiguous RTL, state physical left/right.
  Resolve incompatible requirements before execution; do not silently choose ellipsis or scaling.
- Supersede only conflicting old instructions. Do not restart completed work or replay old examples.

## 2. Live fields and authority

Include the target repository/task/branch/PR, expected SHA when verified, approved source and
physical scope, acceptance conditions, checks, current deferrals and completion boundary.
Mark executor verification outstanding when a live fact is unavailable to the coordinator.
Resolve discoverable facts from GitHub, the task checkout or approved devices; never invent
identifiers, paths, device addresses, versions, signer identity or results.

No unresolved template placeholders may be sent. Ask the owner only for a missing decision or
materially different interpretation that safe inspection cannot resolve. An intent note in the
task record is not a new approval gate.

Use only relevant references. Outside the code block, identify the reference used and list exact
attachment filenames only when needed. Prefer already accessible GitHub/VPS evidence. Image
interpretation requires actual image access; a path string is not proof of image delivery.
Keep model/provider research dated and separate; it authorizes no configuration or tool changes.

## 3. Complete the authorized round

For an owner-authorized Implementation/Correction round, follow root `AGENTS.md`'s standing
workflow unless the current owner instruction explicitly narrows it:

1. Verify live state and instruction scope; trace the actual source owner and cause.
2. Make the smallest correct source change and review the complete diff.
3. Run relevant focused checks and affected regressions. Tests are not deferred by default;
   honor only the current task's explicit deferrals.
4. Build applicable variants and refresh the approved persistent device/package surfaces under
   the physical contract, with truthful source/APK identity and state preservation. A task
   involving documentation only does not require an Android build or device refresh.
5. Retain the frozen candidate, provenance, actual results and limitations in durable task records.
6. Once local validation and Git gates pass, make one coherent commit per authorized correction
   round, use normal fast-forward push and create/update the same single PR. No experimental
   commits, history rewrite, direct official-branch push or commit while task CI is running.
7. Follow configured PR checks until final. For a failure, inspect full relevant logs/artifacts,
   classify the first cause and fix an in-scope defect in the same task/PR. A successful push,
   pending CI or a failed check is not technical completion. If path filters do not trigger CI,
   record NOT RUN with the actual reason; do not manufacture a pass or rerun a successful build.
8. Finish with one factual report. Separate technical completion, owner visual acceptance and
   release qualification. Merge, signing, tags, release and deployment require separate authority.

Continue routine authorized work without repeated permission requests. Persistence never overrides
STOP rules, a real external blocker or protected-action limits; report those precisely.

## 4. Capture and runtime boundary

Screenshots, recordings, frame extraction, montages, screenshot comparison and visual journeys
are OFF unless the owner explicitly authorizes them for the current task. Do not infer permission
from a UI edit, ADB availability, installation, a roadmap gate or a missing capture.

Perform only bounded runtime checks needed for the changed technical contract. Do not run the
capture/open/compare/rebuild loop or a full device/screen census for a routine correction.
Missing captures alone do not block routine technical completion. Record automated visual
validation as `NOT RUN — CAPTURE NOT AUTHORIZED`; owner review defaults to PENDING.
Record ACCEPTED or REJECTED only from an actual owner decision for the exact candidate/scope.
Full visual/release qualification remains unproven until its separately authorized evidence exists.

## 5. Packet and report checklist

A filled packet contains only relevant fields:

- title/type and NEW or RESUME;
- owner observation, exact target and requested result;
- verified live target and explicitly outstanding verification;
- allowed change, preserved work and superseded instructions;
- concrete acceptance criteria and relevant states;
- source/check/build/install/Git/CI scope, current deferrals and capture policy;
- stop conditions, durable evidence location and completion boundary.

The report records cause/uncertainty, changed files, exact candidate/commit/PR, actual checks,
build/APK and installation/launch outcomes, CI conclusion, NOT RUN/BLOCKED items, owner acceptance
and residual risk. Attribute each result to its actor. Builds and CI do not establish visual
acceptance, universal device coverage, decoded media or production readiness.
